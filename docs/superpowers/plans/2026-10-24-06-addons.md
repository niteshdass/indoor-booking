# Plan 06 — Add-ons Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An owner keeps one add-on catalogue, enables each add-on per venue or turf (with an optional price override), and for any turf the API lists the add-ons on offer and prices a selection for a set of slots, with auto-apply rules and stock checks, through a pure `quoteAddons()` that Plan 07's `quoteBooking()` will call.

**Architecture:**
- **Shared package, pure.** Add-on types, line totals, auto-apply matching and `quoteAddons()` live in `packages/shared/src/addons.ts` with no I/O, so Plan 07 and the web app reuse them and tests need no database.
- **API module.** A new `apps/api/src/addons/` module holds the `Addon` (catalogue) and `AddonAssignment` models, their routes, and `offeredAddons()`, which resolves a turf's effective add-ons (turf assignment over venue assignment over catalogue).
- **Stock in use comes from bookings**, which arrive in Plan 07. `quoteAddons()` takes it as an `inUse` input (empty here), the same way `computeSlots` takes `taken`.

**Tech Stack:** Plan 01–05 stack. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-23-sports-slot-booking-design.md`:
- §9 (add-ons: catalogue, per venue/turf enablement with price override, pricing types, stock, auto-apply, snapshot)
- §5 (Manager manages add-ons of assigned venues; `addon.manage`; activity log)
- §16 (`addons`, `addonAssignments`)
- §4 (minor units, venue currency)

Roadmap: `docs/superpowers/plans/2026-10-23-roadmap.md` (Plan 06; failure modes 2 and 5).

## Global Constraints

- **Earlier plans still apply.** TS strict, ESM, error shape `{ error: { code, message, details? } }`, `/api/v1`, injected `services.now()`. Owner routes mount on `ownerRouter`; every query carries `ownerId` (models use the `tenantScoped` plugin). Mutations and their `logActivity` run in one `runInTransaction`.
- **Tenancy.** Another owner's data, or a venue outside the member's scope, gives `404 not_found` and never data (roadmap failure mode 2). Public reads expose only published venues of `active` owners, and only active turfs (`publicVenueBySlug` + `active: true`, as in `publicSlots.ts`).
- **Money.** All prices and totals are integers in minor units (`assertMinor`); no float math (roadmap failure mode 5). A price is only ever charged in the currency it was set in.
- **Business day.** Quoted from spec §7: a slot "belongs to the business day it opened on". Auto-apply time ranges match a slot's local start time by time of day, modulo 1440, exactly like pricing rule ranges (Plan 05 Task 2 ruling).
- **Snapshot.** Quoted from spec §9: "Add-ons are snapshotted onto the booking (name, unit price, qty, total)." `AddonLine` is that snapshot; Plan 07 stores it as is.
- **No UI in this plan.** Plan 12 (checkout) and Plan 13 (add-on catalogue screen) must follow `.superdesign/design-system.md` and `apps/web/src/styles/tokens.css`; add-on names are owner text and may be Russian.

## Decisions made in this plan (builder's calls)

- **Catalogue** (`addons`, one per owner): `name` (1–60, unique per owner, case-insensitive), `pricingType` (`per_booking` | `per_unit` | `per_hour`), `price`, `currency`, `maxQuantity`, `stock`, `autoApply`.
  - `currency` is copied from the owner's `defaultCurrency` at creation and never changes; `price` is in it.
  - `maxQuantity` (1–99, default 10) caps a `per_unit` quantity. Other types always have quantity 1.
  - `stock` (integer 0–9999, or `null` = unlimited) is the number of units one **venue** holds; the pool is shared by the venue's turfs. A booking uses `quantity` units of a `per_unit` add-on and 1 unit of the others, for the booking's whole time.
  - `autoApply: { range?: { start, end }, outdoorOnly: boolean } | null`. Spec example "floodlight added automatically to slots after 6pm on outdoor turfs" = `{ range: { start: '18:00', end: '06:00' }, outdoorOnly: true }`. No `range` = every slot. Allowed only on `per_booking` and `per_hour` add-ons with `stock: null` (else 400): an auto add-on has no quantity for the player to choose and must never fail a booking for stock.
  - Writes (`POST`, `PATCH`, `DELETE /addons`) need `addon.manage` **and** all-venue scope (else 403 `forbidden`): the catalogue price reaches every venue, so a manager limited to some venues cannot change it. Reading the catalogue needs `addon.manage`.
  - `DELETE` is a hard delete and removes the add-on's assignments in the same transaction. Bookings keep their snapshot (Plan 07), so nothing else refers to it.
- **Assignments** (`addonAssignments`): `{ addonId, venueId, turfId: null | id, enabled, priceOverride: number | null, stock: number | null }`, unique per `{ ownerId, addonId, venueId, turfId }`.
  - `turfId: null` is the venue-level assignment; a turf-level one beats it for that turf (so a turf can switch off a venue-wide add-on, or switch one on alone).
  - `stock` override is venue-level only (the pool is per venue); turf-level bodies with `stock` → 400.
  - Writes and the venue listing need `addon.manage` and the venue in scope (outside scope → 404). Writes are upserts by `PUT`; `DELETE` removes one (404 if none).
  - Concurrent assign and catalogue delete: the assign transaction writes the add-on document first (`lockAddon`, like `lockTurf`), so it conflicts with the delete and retries into a 404. No orphan assignment survives.
- **Effective add-on for a turf** (`offeredAddons`): take the turf-level assignment, else the venue-level one; offered only when that one is `enabled`.
  - `unitPrice = turf.priceOverride ?? venue.priceOverride ?? (addon.currency === venue.currency ? addon.price : none)`. With no price in the venue's currency the add-on is **not offered**.
  - `PUT` of an enabled assignment that would resolve to no price → 400 `price_override_required`, so the owner learns at once rather than seeing the add-on silently missing.
  - `stock = venue.stock ?? addon.stock`. `autoApply` with `outdoorOnly` is dropped on indoor turfs.
  - Sorted by add-on name (collation `en`, strength 2).
- **Quoting** (`quoteAddons`, pure):
  - Auto lines come first, in offered order, then the player's selection in the order given.
  - An auto add-on applies to the slots whose `localStart` it covers (modulo 1440). A `per_booking` auto line is charged once if any slot matches; a `per_hour` auto line is charged for the matching slots' minutes only; no match means no line.
  - Selected `per_hour` lines are charged for all the slots' minutes. Minutes are elapsed minutes (`endAt − startAt`), so DST nights bill real time.
  - Totals: `per_booking` = price; `per_unit` = price × quantity; `per_hour` = price × minutes / 60 rounded half up to a whole minor unit (integer math, e.g. 1005 × 90 / 60 = 1507.5 → 1508).
  - Errors (`AddonQuoteError` with `code` and `addonId`): not offered → `addon_unavailable`; an auto add-on in the selection → `addon_auto`; the same add-on twice → `duplicate_addon`; quantity outside 1..`maxQuantity` for `per_unit`, or other than 1 for the other types → `invalid_quantity`; `inUse[addonId] + units > stock` → `addon_out_of_stock`. The API maps `addon_out_of_stock` to 409 and the rest to 400 (Plan 07).
  - `total` is the sum of line totals, checked with `assertMinor`.
- **Carry-over from Plan 05** (deferred minor "turf delete leaves SlotOverride/Closure rows orphaned"): deleting a turf also deletes its slot overrides, turf-level closures and turf-level add-on assignments; deleting a venue (which already requires no turfs) also deletes its venue-level closures and add-on assignments. Same transaction as the delete.

## Not in this plan

- `quoteBooking()`, booking snapshots and computing `inUse` from overlapping bookings at the venue: Plan 07.
- **Plan 07 carry-over (from Plan 05 final review):** an add/modify override about 23 h long can reach business day D+2, which neither the API overlap check (D±1) nor `loadDay` (D−1) looks at. Fix in Plan 07 before slot locks: reject a mapped end past minute 2880, or check D±2.
- Add-on photos, categories, descriptions, per-date add-on prices.

## Review Focus

1. **Venue in another currency.** Owner default BDT, a venue in USD: an add-on enabled there without a price override is refused at `PUT` (400 `price_override_required`) and never appears in the turf's offered list; with a venue or turf override it appears at the override price. (Task 3 tests.)
2. **Tenancy.** Assigning owner B's add-on, or any add-on at a venue outside a manager's scope → 404 with the same body; a manager limited to some venues editing the catalogue → 403. (Task 2 and Task 3 tests.)
3. **Auto-apply across midnight.** Floodlight `per_hour` 1200/h, range 18:00–06:00, outdoor turf, 60-min slots starting 17:00, 18:00 and (past midnight, same business day) 01:00 → one auto line of 120 minutes, total 2400; the same add-on on an indoor turf with `outdoorOnly` → no line. (Task 1 tests.)
4. **Rounding and three-decimal money.** `per_hour` 1005 for a 90-min slot → 1508; a total above `Number.MAX_SAFE_INTEGER` throws. (Task 1 tests.)
5. **Stock.** Stock 3 with `inUse` 2: quantity 1 passes, quantity 2 → `addon_out_of_stock`; stock 0 → never passes; `stock: null` ignores `inUse`. (Task 1 tests.)
