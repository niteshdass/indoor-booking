# Search API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A public `GET /api/v1/search` that finds published venues by distance and filters, and gives each result its distance, starting price and next free slot.

**Architecture:**
- A MongoDB aggregate on `venues` picks the candidates, in order and filtered at the venue and turf level:
  - `$geoNear` on the existing `2dsphere` index when a location is given, otherwise name order;
  - only published venues of active owners;
  - only venues with at least one active turf that matches the sport and indoor filters.
- For each candidate, the route computes the business day of every matching turf with the existing `loadDay`. A pure `summarizeDay` function then applies the time and price filters, and works out `fromPrice` and `nextFreeSlot`.
- Paging uses a scan cursor (the number of candidates walked). The day-level filters run in app code, so a page can be shorter than `limit` while more remain.

**Tech Stack:** Express, Mongoose 8 aggregate (`$geoNear`, `$lookup`), Zod 3, Vitest + supertest on the replica-set test DB.

**Spec:** `docs/superpowers/specs/2026-10-23-sports-slot-booking-design.md` §13 (also §5 for public reads, §7 for slots and past-midnight hours, §8 for pricing).

## Global Constraints

- REST JSON under `/api/v1`, mobile-friendly; it needs no auth.
- Player-facing reads only expose published venues (§5), and only of owners with `status: 'active'` (same rule as `publicVenueBySlug`).
- Every cross-tenant query opts out of the tenant filter explicitly, with `.setOptions({ crossTenant: true })` on queries and `.option({ crossTenant: true })` on the aggregate. Never add a fake `ownerId` filter to get past the plugin.
- Money is integers in minor units with an ISO 4217 code, never floats. Prices from different currencies are never compared with each other.
- Slot times are computed in the venue's timezone. A slot belongs to the business day it opened on (§7). Use `loadDay` from `apps/api/src/schedule/load.ts`; don't re-implement slot rules.
- The clock comes from `services.now()`, never `new Date()`, in route code.
- Test command for one file: `node_modules/.bin/pnpm --filter api exec vitest run <path>` (run from the repo root). Whole suite: `node_modules/.bin/pnpm test`. Also run `node_modules/.bin/pnpm typecheck` and `node_modules/.bin/pnpm lint`.
- Fake clock in tests: `makeTestServices()` starts at `2026-01-01T00:00:00Z`. That is Thu 06:00 in `Asia/Dhaka` and Wed 2025-12-31 16:00 in `America/Los_Angeles`. Default hours are 08:00–22:00 every day, with weekend days sat and sun.

## Builder's calls (made here, open to change)

- **Query parameters** (all optional):

  | Parameter | Meaning |
  |---|---|
  | `lat`, `lng` | Must come together. |
  | `radiusKm` | 0 < r ≤ 500; needs `lat`/`lng`. Omitted means "anywhere". |
  | `sport` | One of `SPORTS`. |
  | `indoor` | `true` or `false`. |
  | `date` | `YYYY-MM-DD` venue-local business date. Omitted means each venue's own local today. |
  | `from`, `to` | `HH:MM`, together, not equal; `to <= from` crosses midnight. A slot matches if it **starts** in `[from, to)`. |
  | `currency` | ISO 4217; keeps only venues in that currency. |
  | `minPrice`, `maxPrice` | Integer minor units; need `currency`; inclusive; `min <= max`. |
  | `available` | `true` means only venues with a free slot. |
  | `limit` | 1–50, default 20. |
  | `cursor` | Integer ≥ 0, default 0. |

  Unknown or repeated parameters → 400 `validation_error`.
- **One date only:** "next free slot" is the earliest free slot on the searched date, not a scan of later days. It is `null` when that day has none.
- **Matching slot:** a slot of a matching turf on an open day (not closed, inside the booking window) that:
  - has a non-null price;
  - has a status of `available`, `pending` or `booked`;
  - starts inside the time range, if one is given;
  - has a price inside the price range, if one is given.
- **Starting price:** `fromPrice` is the lowest price among matching slots, booked ones included.
- **Next free slot:** `nextFreeSlot` is the earliest `available` matching slot, ordered by start time and then turf name.
- **When a venue is dropped:**
  - Without `from`/`to`, a price range or `available=true`, every candidate is returned, even one closed that day.
  - With a time range or price range, a venue needs at least one matching slot.
  - With `available=true`, it needs a `nextFreeSlot`.
- **Distance:** `distanceMeters` is an integer (rounded), or `null` without a location. The web formats it.

## Review Focus

1. **Paging when results are filtered out.** Venues dropped by the day filters must still move the cursor forward. Walking the pages must return every venue exactly once and end with `nextCursor: null`. Covered in Task 4: `'filtered-out venues still advance the cursor'` and `'limit 1 walks every venue once'`.
2. **Venues in different timezones with no `date`.** Each venue uses its own local today, not the server's date. Covered in Task 4: `'date defaults to each venue's local today'`.
3. **A time range crossing midnight** (for example 22:00–02:00, or a 16:00–02:00 night session searched at 00:00–02:00). The slot after midnight belongs to the session's business day and matches. Covered in Task 2: `'time range across midnight matches the night session'`; Task 4: `'night session slot after midnight is found on its business day'`.
4. **Hidden venues never leak:**
  - unpublished venues;
  - venues of suspended owners;
  - venues whose only turfs are inactive or don't match.

  All of these stay out of results, and the response holds only public fields. Covered in Task 3: `'only published venues of active owners with an active matching turf'`; Task 4: `'result shape: public fields only'`.
5. **Prices in mixed currencies.** A price filter without `currency` is a 400, and venues in other currencies are excluded. Covered in Task 1: `'price range needs a currency'`; Task 3: `'currency filter keeps only that currency'`.

### Task 3: Candidate venues aggregate

**Files:**
- Create: `apps/api/src/search/candidates.ts`
- Modify: `apps/api/test/helpers/venues.ts`
  - `seedVenue` gets `location?: [number, number]` (lng, lat) and `published` is unchanged.
  - `seedTurf` gets `sports?: Sport[]`.
  - Existing callers must keep their defaults.
- Test: `apps/api/test/search/candidates.test.ts`

**Interfaces:**
- Consumes: `SearchQuery` (Task 1); `Venue`, `Turf`, `Owner`.
- Produces:
  - `type Candidate = { venue: VenueDoc; turfs: TurfDoc[]; distanceMeters: number | null }`. The documents are hydrated (`Venue.hydrate`, `Turf.hydrate`) so they can go straight to `loadDay`.
  - `findCandidates(q: SearchQuery, skip: number, n: number): Promise<Candidate[]>`. The pipeline, in order:
    1. `$geoNear` when `q.near` is set:
       - `near` is a GeoJSON point `[lng, lat]`;
       - `spherical: true` and `distanceField: 'distanceMeters'`;
       - `maxDistance: radiusKm * 1000` when a radius is given;
       - `query: { published: true, currency? }`.

       Otherwise `$match` the same query.
    2. `$lookup` owners, then keep `status: 'active'`.
    3. `$lookup` turfs with `ownerId`, `venueId` and `active: true`, plus `sports: sport` and `indoor` when they are set, sorted by name. Keep venues where at least one turf remains.
    4. `$sort`: `{ distanceMeters: 1, _id: 1 }` with a location, `{ name: 1, _id: 1 }` without.
    5. `$skip skip`, then `$limit n`.

    Run it with `Venue.aggregate(...).option({ crossTenant: true })` (the tenant plugin reads `options.crossTenant`). Round `distanceMeters`.

### Task 4: `GET /api/v1/search`

**Files:**
- Create: `apps/api/src/search/routes.ts`
- Modify: `apps/api/src/app.ts` (`api.use(searchRouter(deps.services))`, next to the other public routers)
- Test: `apps/api/test/search/search.test.ts`

**Interfaces:**
- Consumes:
  - `parseSearchQuery` (Task 1), `summarizeDay` (Task 2), `findCandidates` (Task 3);
  - `loadDay` and `inWindow` from `schedule/load.ts`;
  - `localParts` and the `SearchResult` / `SearchResponse` types from shared.
- Produces:
  - `searchRouter(services: AppServices): Router`, handling `GET /search`, which answers `SearchResponse`;
  - `export const searchConfig = { scanBatch: 100 }`, which tests lower.
- Algorithm:
  1. Fetch `findCandidates(q, q.cursor, searchConfig.scanBatch)`.
  2. Walk the candidates in order, one venue at a time. For each:
     - `date = q.date ?? localParts(now, venue.timezone).date`;
     - for each turf, call `loadDay(ownerId, venue, turf, date, now)`;
     - `open = !day.closed && inWindow(date, now, venue.timezone, settings.bookingWindowDays)`;
     - summarize, then apply the "When a venue is dropped" rules.
  3. Stop once `q.limit` results are collected.
  4. Set `nextCursor`:
     - `q.cursor + walked` if `walked < candidates.length` or `candidates.length === scanBatch`;
     - otherwise `null`.
  5. Build each result:
     - `photo` is the first photo (with `alt` only when set) or null;
     - `sports` is the union of the matching turfs' sports, in `SPORTS` order.
